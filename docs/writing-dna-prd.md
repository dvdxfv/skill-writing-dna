# Writing DNA PRD

## 1. 产品定位

`writing-dna` 是一个“个人写作风格保真”型 skill。

它只做一件事：

先读取用户过去亲自写的文章，提取出这个用户的写作 DNA；再读取一篇新的 AI 草稿，按这个 DNA 去改写，让新文章在尽量不改变原意的前提下，更像用户本人写的。

一句话定义：

`保留内容意思，把文章味道改得更像我。`

## 2. 核心问题

现在 AI 写作最大的问题不是“写不出来”，而是：

- 写得太像 AI
- 写得不像用户本人

用户真正的需求不是泛泛地“去 AI 味”，而是：

`拿我过去真实写过的文章当证据，提取我的风格，再把新的 AI 草稿改到接近我的声音。`

## 3. 当前用户需求

当前这个项目的真实需求已经明确，不再发散：

1. 读取我个人过去写过的文章。
2. 从这些文章里提取我的写作 DNA。
3. 再拿一篇新的 AI 写出来的文章。
4. 根据我原来的文章风格，把这篇新文章改得和我的味道对得上。

这里的重点不是“万能改写”，也不是“批量内容生产”，而是：

`旧文风格提取 -> 新文风格贴合`

## 4. 产品目标

V1 必须完成一条闭环：

1. 输入 5 到 10 篇用户旧文。
2. 输出一份可复用的 DNA 文件。
3. 输入一篇新的 AI 草稿。
4. 检测这篇草稿里的 AI 套话和风格偏差。
5. 根据 DNA 重写该草稿。
6. 输出最终稿和对比结果。

## 5. 成功标准

这个 skill 只有在以下条件同时成立时，才算做成：

- 用户可以用自己的旧文成功生成 DNA 文件。
- 用户可以把新的 AI 草稿和 DNA 文件一起喂给系统。
- 系统能输出一篇改写后的文章。
- 用户主观判断这篇改写稿明显比原始 AI 草稿更像自己。
- 改写后不应明显丢失原文的核心信息、判断和结构。

## 6. 范围内

当前版本只做以下能力：

- 读取本地 `.md` / `.txt` / `.docx` 旧文
- 把 `.docx` 稳定转换成可读 Markdown，作为统一输入层
- 过滤表格、图片、图注等非正文内容
- 清洗文本
- 提取写作 DNA
- 检测 AI 套话
- 根据 DNA 改写新文章
- 输出 DNA、改写稿、检测结果、对比结果

## 7. 明确不做

当前版本一律不做这些内容：

- 发帖自动化
- 浏览器自动操作
- 图床上传
- 多平台分发
- SEO 优化
- 热点选题
- 爆款预测
- 外部 API 自动发布
- 泛化成“大而全内容工作流”

判断原则只有一个：

如果某个功能不能直接增强“旧文 -> DNA -> 新稿贴合改写”这条链路，就不进入当前 PRD。

## 8. 功能需求

### 8.1 DNA 提取

系统必须支持：

- 输入多个旧文文件，或一个包含旧文的目录
- 自动读取文章文本
- 当输入是 `.docx` 时，必须先转换为可读 Markdown，再进入后续流程
- 在进入 DNA 提取前，默认过滤表格、图片、图片说明、图题、附件痕迹等非正文内容
- 过滤 markdown 噪声
- 提取风格特征
- 生成一份 DNA JSON 文件

DNA 至少应包含：

- 标志短语
- 句长倾向
- 段落节奏
- 常见开头方式
- 常见结尾方式
- emoji 使用倾向
- 用户不常用、但 AI 常见的套话黑名单

### 8.1.1 DOCX 转 Markdown 输入层

系统必须提供一个单独的输入标准化工具，负责把 `.docx` 转成 Markdown。

这个工具的要求是：

- 输入是 `.docx`
- 输出是 `.md`
- 输出结果必须是人能直接阅读和检查的
- 输出结果必须适合作为后续 DNA 提取的输入
- 不以 JSON 作为主输出格式
- 转换过程中要尽量保留正文层级，但默认不把表格和图片当作 DNA 提取输入

这样整个系统的输入链路统一为：

`docx / md / txt -> 标准 markdown -> DNA 提取 -> AI 草稿改写`

之所以要转 Markdown，而不是直接转 JSON，原因很明确：

- Markdown 既适合脚本继续处理
- 也适合人直接查看、人工校对、手动修正
- 能作为中间可审计产物，防止输入层悄悄出错

### 8.1.2 非正文过滤层

系统必须在 DNA 提取之前增加一层“非正文过滤”。

目标很明确：

- 我们要提取的是人的文字风格
- 不是版式风格
- 不是表格字段风格
- 不是图片内容
- 不是图注或附件说明

因此默认需要过滤的内容包括：

- 表格
- 图片
- 图片占位符
- 图题
- 图注
- 附件说明
- 自动编号目录
- 页眉页脚
- 页码
- 重复性模板字段

对于绩效评价、汇报、公文、制度类文档，这一层尤其关键。
因为这类文档常常包含大量结构性表格、固定栏目、配图和格式性说明。
如果不先过滤，提取出来的就不是“作者 DNA”，而是“模板噪声”。

### 8.1.3 模板过滤与个人表达分离

系统不能把整篇文档直接当成 DNA 样本。

必须先区分两类内容：

1. 模板性内容
2. 个人表达内容

模板性内容要尽量识别并降权或剔除，个人表达内容才进入 DNA 提取。

这里的原则是：

`模板决定这类文档应该怎么写，DNA 决定你在这个模板里习惯怎么写。`

### 8.2 AI 味检测

系统必须支持：

- 输入一篇新的 AI 草稿
- 输出 AI 味评分
- 输出命中的套话、组合套话、句式套话
- 输出可用于排查的命中上下文

### 8.3 风格贴合改写

系统必须支持：

- 输入一篇 AI 草稿
- 输入一份 DNA 文件
- 生成一篇更贴近用户风格的新稿

改写时必须遵守：

- 尽量保留原文核心信息
- 优先去掉明显 AI 套话
- 尽量贴近用户旧文的句长、节奏、短语习惯
- 不为了“像”而胡乱添加原文没有的信息

### 8.4 输出物

系统最终至少要能产出：

- `用户名-dna.json`
- 改写后的文章
- AI 味检测结果
- 对比/调试结果

## 9. 非功能要求

- 必须能在本地运行
- 必须适配当前 Windows 工作区
- 必须尽量使用 UTF-8
- `.docx -> .md` 的转换结果必须优先保证可读性，而不是追求复杂格式百分百还原
- 表格和图片默认不进入 DNA 提取主链路，除非用户明确要求保留
- 不能依赖浏览器登录态
- 核心闭环不能依赖第三方平台 API
- 命令行输出不能因为 Windows 终端编码问题直接崩掉

## 10. 当前最大风险

### 10.1 编码风险

这是当前项目第一优先级风险。

当前工作区里有两类文件：

- 我现在新写的文件
- 你从 Claude 下载下来的历史产物

其中，历史产物里已经明确存在乱码污染。这个问题要分清：

1. 有些是“终端显示乱码”
2. 有些是“文件内容本身已经乱码”

第二种更严重。

如果源文件本身已经乱码，那么后续脚本虽然能跑，也只是“对乱码做处理”，结果不可信。

所以后续实现必须遵守这个边界：

- 代码结构问题可以继续推进
- 但语义依赖强的样本、词典、说明文档，必须先恢复成可读 UTF-8，或者明确重写

### 10.2 风格判断具有主观性

“像不像我”这件事天然带有主观性，所以最终必须保留人工复核。

### 10.3 样本质量决定上限

如果旧文数量太少、质量不稳定、题材差异太大，DNA 质量就会受影响。

## 11. 验收标准

第一轮验收按这个用例走：

1. 准备 5 篇用户旧文。
2. 生成 1 份 DNA 文件。
3. 准备 1 篇新的 AI 草稿。
4. 生成 1 篇改写稿。
5. 用户人工判断改写稿是否明显比原始 AI 稿更像自己。

只有脚本能跑不算通过。
必须是“结果也对味”，才算通过。

## 12. 开发顺序

后续实现按这个顺序推进，不能乱：

1. 先冻结 PRD
2. 补齐 `.docx -> .md` 输入层
3. 处理编码问题
4. 稳定 DNA 提取
5. 稳定 AI 味检测
6. 实现改写流程
7. 实现报告和对比输出
8. 跑一轮完整验收

## 13. 决策规则

后面只要出现“要不要做这个功能”的分歧，就按这一条判断：

`凡是能直接增强“读取旧文 -> 提取 DNA -> 改写新稿更像本人”这条链路的，就保留；否则就排除。`
