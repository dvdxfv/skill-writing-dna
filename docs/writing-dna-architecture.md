# Writing DNA 架构说明

## 1. 文档目的

这份文档不是功能清单，而是当前项目的架构基线。

作用只有两个：

1. 防止后续开发过程跑偏
2. 明确哪些部分是硬约束，哪些部分允许调整

后续如果实现与本架构冲突，默认以这份架构文档为准；如果要改，先讨论，再改文档，再改代码。

## 2. 项目总目标

这个项目只服务一条主链路：

`用户旧文 -> 提取个人 DNA -> 输入新 AI 草稿 -> 输出更像用户本人风格的新稿`

任何新增功能，只有在直接增强这条链路时，才允许进入当前版本。

## 3. 总体架构

当前架构分为 6 层：

1. 输入层
2. 标准化层
3. 过滤层
4. 模板识别层
5. DNA 提取层
6. 草稿改写层

## 4. 分层说明

### 4.1 输入层

负责接收原始材料。

当前允许的输入类型：

- `.docx`
- `.md`
- `.txt`

输入层只负责“接住文件”，不负责直接提 DNA。

### 4.2 标准化层

负责把不同输入统一成 Markdown。

目标不是生成 JSON，也不是做复杂结构抽取，而是生成：

- 人能看懂
- 机器能继续处理
- 可审计
- 可手动修正

的标准 Markdown 中间稿。

统一后的链路必须是：

`docx / md / txt -> markdown`

### 4.3 过滤层

负责去掉不属于“写作风格”的噪声。

默认过滤对象：

- 表格
- 图片
- 图片占位符
- 图题
- 图注
- 附件说明
- 页眉页脚
- 页码
- 自动目录
- 明显重复的模板字段

这层的目标不是“让文档更好看”，而是避免 DNA 被非正文污染。

### 4.4 模板识别层

负责区分：

1. 这类文档本来就固定的结构
2. 作者个人表达出来的风格

对绩效评价、汇报、公文、制度类文档，这层是必要层，不是可选层。

必须明确：

- 模板不是 DNA
- 模板里的固定表达不应高权重进入 DNA
- 个人在模板中的判断、转折、强调、收尾，才是 DNA 候选

### 4.5 DNA 提取层

负责从“过滤后、剥离模板后的正文”中提取个人风格。

DNA 提取对象应重点关注：

- 标志短语
- 转折习惯
- 判断句风格
- 结论写法
- 句长倾向
- 段落节奏
- 常见开头
- 常见结尾
- emoji 使用倾向
- 明显不属于作者习惯的 AI 套话黑名单

DNA 的本质不是“复刻整篇旧文”，而是抽出可复用的个人表达规律。

### 4.6 草稿改写层

负责处理新的 AI 草稿。

这层不只是“去 AI 味”，而是：

1. 保留原文核心意思
2. 去掉明显 AI 套话
3. 让表达方式更贴近用户 DNA

如果文档类型本身有模板要求，还必须同时满足：

- 像这类业务文档
- 也像这个人写的

## 5. 架构中的硬约束

下面这些是写死的，后面不能随意改：

### 5.1 主目标不能改

本项目不是泛内容生产工具，不是自动发帖工具，不是多平台分发工具。

主目标固定为：

`旧文提 DNA，新稿按 DNA 改写`

### 5.2 Markdown 是统一中间层

`.docx` 不直接进 DNA 提取。

必须先转 Markdown。

原因：

- 可读
- 可审计
- 可人工修
- 可做后续过滤和模板剥离

### 5.3 表格和图片默认不进 DNA

这是硬规则。

除非用户明确指定保留，否则：

- 表格不进入 DNA 主链路
- 图片不进入 DNA 主链路
- 图注不进入 DNA 主链路

### 5.4 模板内容不能直接当成 DNA

尤其在绩效评价类文档里，这条必须写死：

`模板性内容 != 作者 DNA`

DNA 只能从模板之外，或模板内部的个人表达差异中提。

### 5.5 输出必须有人可读的中间产物

系统不能只吐内部结构化数据。

至少要保留：

- Markdown 中间稿
- DNA 文件
- 改写结果
- 对比/调试结果

因为这个项目不是全黑箱自动化，用户需要能看、能检查、能修。

### 5.6 对话框智能交互是产品形态的一部分

这个项目不是单纯给开发者手动跑脚本的 CLI 工具，而是主要在工具对话框里使用的 skill。

因此“足够智能地对话”不是附加体验，而是架构硬约束：

- 先从本轮对话判断用户意图，再决定进入 DNA 提取还是草稿改写
- 先检查用户是否已经上传文件、粘贴文本或给出目录，再决定是否追问
- 信息不足时只问必要问题，不把完整流程拆成一串让用户选择的命令
- 在模板剥离确认、DNA 画像确认和改写效果确认三个节点必须停等用户判断
- 关键产物必须在对话中用摘要、图片语法和完整路径交代清楚
- 脚本执行细节默认由 skill 处理，只有排查或用户主动要求时才展开

## 6. 架构中的可调部分

下面这些是可以灵活讨论和调整的：

### 6.1 DOCX 转 Markdown 的具体实现

写死的是“必须转成 Markdown”。

不写死的是：

- 用哪套库
- 转换精度做到什么程度
- 是否保留部分简单列表或简单表头信息

### 6.2 过滤强度

写死的是“表格、图片默认过滤”。

不写死的是：

- 页眉页脚是否全过滤还是按规则过滤
- 某些短图注是否保留到备注区
- 某些固定栏目是否直接删掉还是先标记再删

### 6.3 模板识别策略

写死的是“模板和个人表达必须分离”。

不写死的是：

- 用规则识别
- 用重复片段统计识别
- 用多篇文档交集识别
- 先人工标注模板区再自动化

### 6.4 DNA 特征权重

写死的是“DNA 要从个人表达里提”。

不写死的是：

- 标志短语权重大一些还是句长权重大一些
- 段落节奏怎么计分
- 黑名单怎么扩展
- 开头和结尾模式权重多大

### 6.5 改写强度

写死的是“新稿要更像用户本人”。

不写死的是：

- 轻改
- 中改
- 深改

也就是说，改写力度可以调，但方向不能变。

### 6.6 长文分段改写

写死的是“长文不能整篇塞给模型、不能擅自重组结构”。

不写死的是：

- 按二级标题切
- 按章节块切
- 按段落组切

当前实现口径是 prompt 层协议：长文触发时先告知用户“按章节改”，逐块改写，最后统一回查术语、事实数字、产品名、引用对象、标题层级和跨章节指代。这里不改 `rewrite_with_dna.py` 的执行顺序，避免影响既有短文改写结果。

### 6.7 交互可见性

功能只存在于文件里不算完成，必须在对话里有入口。当前要求：

- DNA 保存后提示可“用回上一版”
- 改写前提示发布场景和保守度可调
- 改写报告里如有规则被跳过或降权，要说明“有 N 条规则这次没应用”
- 长文触发分段时要说明“按章节改”
- 脚本命令由模型执行，面向写作者只报告人话结论

## 7. 当前推荐模块拆分

为了避免逻辑堆在一个脚本里，当前推荐拆成这几个模块：

- `docx_to_md.py`
- `filter_non_prose.py`
- `strip_template.py`（跨文档对齐 · 通用模板剥离 · PRD §8.1.3 Layer 1）
- `test_sample_sufficiency.py`（样本质量预检 · 多维健康度 · DNA 提取前的闸门）
- `extract_dna.py`
- `dna_versioning.py`
- `detect_ai_slop.py`
- `rewrite_with_dna.py`
- `generate_report.py`

其中前 3 个是输入治理层，`test_sample_sufficiency.py` 是提取前的样本质量闸门，`dna_versioning.py` 负责 DNA 指针和历史版本，后 4 个是风格处理层。

## 8. 当前决策规则

后面如果出现“这个功能要不要加”的分歧，按下面规则判断：

### 8.1 直接保留

如果它能直接增强以下任一能力，就可以进入讨论：

- 输入更稳定
- 模板识别更准
- DNA 更准
- 改写结果更像用户本人

### 8.2 直接排除

如果它主要服务于以下方向，当前版本直接排除：

- 自动发帖
- 浏览器自动操作
- 内容分发
- SEO
- 热点运营
- 平台增长
- 外部平台集成

## 9. 开发纪律

后续开发必须遵守这个顺序：

1. 先确认架构
2. 再确认 PRD
3. 再拆模块
4. 再动代码

如果中途发现架构不合理，处理顺序也必须是：

1. 先指出冲突
2. 先讨论
3. 先改架构文档
4. 再改实现

不能边写边漂移。

## 10. 当前结论

目前这套架构里，真正写死的只有 6 件事：

1. 项目主目标写死：旧文提 DNA，新稿按 DNA 改写
2. Markdown 中间层写死：所有输入统一先落 Markdown
3. 表格和图片默认过滤写死
4. 模板内容不能直接当 DNA 写死
5. 输出必须保留人可读中间产物写死
6. 对话框智能交互写死：skill 必须主动判断、执行、停等确认，而不是把用户当成命令行操作者

其他实现策略都可以讨论，但不能突破这 6 条底线。
